## 1. Choix du numéro de version

Versionnage sémantique (voir [CONTRIBUTING.md](../../CONTRIBUTING.md), section 4) : **`v1.0.0` → `v1.1.0`**.

- Nouvelle fonctionnalité → on incrémente `Y`.
- Rétrocompatible → on ne touche pas à `X` : les routes existantes ne changent pas, `GET /products` ajoute seulement un champ, et une commande n'est refusée que si le producteur a déclaré un stock.

## 3. Risques de cette mise en production

| Risque | Mesure |
|---|---|
| La migration bloque les commandes existantes (répétition de l'incident d'août) | Stock non déclaré = `NULL` = aucune limite : les 1 200 produits existants restent commandables. Vérifié en staging (`"stock": null`). |
| La migration empêche le retour arrière | Migration additive (ajout d'une colonne) : la version `v1.0.0` fonctionne avec la nouvelle base, pas de restauration nécessaire (R3). |
| Deux commandes simultanées consomment le même stock | Verrouillage de la ligne produit pendant la commande (`SELECT ... FOR UPDATE`). |
| Perte de données en cas de problème | Sauvegarde automatique de la base par le pipeline avant le déploiement en production (R3). |
| Retour arrière trop lent (contrainte : < 5 min) | Rollback = redéploiement de l'image `v1.0.0` déjà publiée, sans rebuild. L'approbateur doit rester disponible pendant la mise en production : le rollback en production demande aussi une approbation. |
| Serveur indisponible | Le PC serveur doit être allumé, avec Docker Desktop et le runner lancés. |

## 5. Déploiement en staging et test de fumée

**Test de fumée automatique** (job `deploy-staging`, script `deploy/smoke_test.sh`) :
- `/health` répond et renvoie la version attendue ;
- `GET /products` renvoie au moins un produit ;
- `POST /orders` renvoie 201 (commande créée) ou 409 (refus pour stock insuffisant).

**Tests manuels de la user story en staging** (`http://localhost:8001`) :

| Test | Commande | Attendu | Obtenu |
|---|---|---|---|
| Version déployée | `curl localhost:8001/health` | `"version":"v1.1.0"` | ✅ `main-91a9d6d` après le merge de #5 (à revérifier en `v1.1.0` après le tag) |
| Déclarer un stock | `curl -X PUT localhost:8001/products/10/stock -H "Content-Type: application/json" -d "{\"stock\": 3}"` | 200, `"stock":3` | ✅ `{"id":10,...,"stock":3}` |
| Commande dépassant le stock | `curl -X POST localhost:8001/orders -H "Content-Type: application/json" -d "{\"product_id\": 10, \"quantity\": 5}"` | 409, `Stock insuffisant pour le produit 10 : 3 disponible(s), 5 demandé(s)` | ✅ 409, `Stock insuffisant pour le produit 10 : 3 disponible(s), 5 demandé(s)` |
| Commande dans le stock | idem avec `"quantity": 2` | 201, stock restant = 1 | ✅ 201, puis `"stock":1` |
| Produit sans stock déclaré | commande sur un produit dont `"stock": null` | 201 (aucune limite) | ✅ produit 500 (`"stock":null`), 50 unités → 201 |

## 6. Mise en production

1. Tag `v1.1.0` sur `main` → le pipeline rejoue : secrets, lint, test, build, staging.
2. Vérification des critères go / no-go.
3. **Approbation** dans GitHub (*Review deployments* → `production`) par l'approbateur.
4. Le pipeline sauvegarde la base, applique les migrations, déploie, puis lance le test de fumée.
5. Vérification : `curl localhost:8000/health` → `"version":"v1.1.0"`.
6. Publication de la Release GitHub `v1.1.0`.

## 7. Plan de retour arrière

| | |
|---|---|
| **Qui le déclenche** | N'importe lequel des développeurs qui constate le problème |
| **Quand** | Test de fumée en échec, erreurs sur les commandes, ou comportement non conforme constaté après la mise en production |
| **Comment** | GitHub → Actions → workflow **Rollback** → *Run workflow* → environnement `production`, version `v1.0.0` → approbation → redéploiement + test de fumée automatique |
| **En combien de temps** | Objectif < 5 min (testé en local : 12 s de déploiement, hors délai d'approbation) |
| **Base de données** | Pas de restauration nécessaire : `v1.0.0` ignore la colonne `stock`. La sauvegarde du pipeline (`tp2-backups/`) ne sert qu'en cas de corruption des données. |

**Ce que le retour arrière ne sait pas annuler :**
- Les commandes passées entre la mise en production et le rollback restent en base.
- Pendant le retour en `v1.0.0`, le stock n'est plus vérifié ni décrémenté : au redéploiement de `v1.1.0`, le stock affiché ne tient pas compte des commandes passées entre-temps. Il faudra le faire redéclarer par les producteurs concernés.

## 8. Démonstration du retour arrière

Point de départ : production en `v1.1.0` (`/health` → `"version":"v1.1.0"`), approuvée par Pierre, sauvegarde de la base `production-20261119-174016.sql`.

| Étape | Action | Preuve que le service fonctionne |
|---|---|---|
| 1 | En `v1.1.0` : déclarer un stock de 2 sur le produit 20, puis commander 5 unités | 409 `Stock insuffisant pour le produit 20 : 2 disponible(s), 5 demandé(s)` |
| 2 | Workflow **Rollback** → `production`, version `v1.0.0` → approbation | Test de fumée du job OK ; `/health` → `v1.0.0` |
| 3 | Vérifier le service en `v1.0.0` : `GET /products`, puis la même commande de 5 unités | Produits sans champ `stock` ; commande acceptée (201) : l'ancienne version ne gère pas le stock |
| 4 | Workflow **Rollback** → `production`, version `v1.1.0` → approbation | Test de fumée du job OK ; `/health` → `v1.1.0` |
| 5 | Refaire la commande de 5 unités sur le produit 20 | 409 : la fonctionnalité est revenue et le stock déclaré a été conservé, sans restauration de la base |

Le redéploiement d'une image déjà publiée prend quelques secondes (12 s mesurées lors des tests) : le délai de retour arrière dépend surtout de la disponibilité de l'approbateur, qui reste joignable pendant la mise en production.
